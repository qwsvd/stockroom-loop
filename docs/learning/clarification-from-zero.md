# 从“要几件”到一笔可核验的订单

先在仓库根目录运行 `python order_demo.py`。默认使用本地规则，不会调用模型。复制下面的三步试一遍。

1. 输入 **请预留茶，有效期不早于2026-12-01，优先早到期。** 看看程序问的是哪一项。它已经知道商品、日期和优先级。
2. 回答 **要3件**。屏幕会显示这次订单的四个字段和一次性的确认文字。此时数据库里仍然没有预留。试着输入 **重下：请预留茶，要2件，有效期不早于2026-12-01，优先早到期。** 看数量和确认码怎样变化。
3. 只在同意新订单时，输入最新显示的“确认”和对应码。观察实际批次、预留数量和最终状态。要体验模型提取，用已有 ChatGPT 登录执行 `python order_demo.py --model`，它会消耗现有推理额度。

再做一个故意失败的例子：在完整订单后加上 **送到我家**。系统只负责预留，运送要求使整单不能自动执行。换成 **3件或5件**，则要先问清件数。回答 **都行** 仍无法批准写入。对不能识别的表述，请以 **重下：** 开头提供完整的新订单。这里的日期表示商品至少有效到哪天，不是下单时间。

阅读源码时跟踪这三个问题：谁提出字段，谁有权写入，谁证明写对了？order_language.py 描述模型输出格式并检查语言依据。order_session.py 保存当前版本；confirm 才能开启写事务。旧版 study.plan 选择批次，study.grade 在提交前检查真实 SQL 行。order_eval.py 另用展开库存单位的算法核对已写入结果。

不要把实验里的自动确认当成现实的用户授权。实验有预先写好的标准答案，一个模拟用户只会同意完全匹配的预览。互动演示依赖操作者亲自核对。你可以运行 `python -m unittest test_orders -v`，看错误 JSON、过期确认、未解决的含糊回答和核验失败如何停在写入之前或触发回滚。

试着不用看报告回答：当规则解析器和模型都提出正确问题，实验能说明是哪一部分带来了额外履约吗？用报告中的“规则也允许提问”一行检验你的答案。
