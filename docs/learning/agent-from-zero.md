# 从一张订单开始理解 Agent

先用纸做一次。有人要 3 件当天还有效的茶。A 批有 2 件，B 批有 4 件，A 更早过期。写出你的分配。如果等你去取时 A 只剩 1 件，旧计划还可行吗？可以问仓库一次，也可以一开始就猜。把两种做法的结果记下，再读下面的代码。

**语言模型（LLM）** 学习文本中的统计规律，根据已有输入生成后续符号。它可以读懂订单、表达计划，也可能给出貌似合理的错误数字。它读到“库里有两件”时拿到的是一条消息，消息可能已经过时。

**工具调用** 把一个决定表示成程序能检查的请求。例如模型写出 `{"op":"inspect"}`，Python 检查动作后才读取库存。文本本身不会改变数据库。业务工具必须核对允许的操作、字段、数量和当前状态。对账户、文件或数据库的权限由运行程序控制。

**Agent 和循环** 在这里指能根据环境观察选择下一步行动的系统。一张固定的操作清单也能成功，但它在第二步失败时只能照旧执行或停止。循环保存动作和反馈，再把它们交给策略。策略可以是人、传统算法或模型。写循环不等于写出了一个新的语言模型。

```python
history = []
for step in range(9):
    action = policy(order, history)
    observation = environment.apply(action)
    history.append((action, observation))
    if "terminal" in observation:
        break
```

上面只有骨架。完整实现还要核验终态、记录错误和预算耗尽。沿着 study.py 的 trial 阅读，找出相应分支。模型可能说“缺货”，核验器必须用可用且合格的总量复查。

**观察和恢复**。提交被拒绝时，旧观察无法解释目前还能分配多少。再检查一次，重新求解，用新计划提交。已经成功的请求不要盲目重复。这里整单提交，要么全生效，要么全不生效，成功后即停止。真正连接远端库存时，如果超时意味着“可能已经写入”，需要请求标识、状态查询和对账；一味重试可能重复发货。

**独立核验**。分配算法先排序再取货。另一个检查办法是问：数量守恒吗？有没有漏掉更优先的库存，却已经取走了优先级较低的库存？手算、不同算法和故意改坏一行再测试，分别能发现不同错误。共享的业务说明仍可能写错。

**评价**。固定题目和规则，把观测、失败、决策数和用时都留下。成功率的分母包括失败。正确报告缺货可完成判断任务，却没有交付商品，所以要另报实际履约数。用相同种子给两个策略同一道题，再逐题比较。重放完全相同的选择不算一次新的模型实验。

**Harness** 是让策略能工作的外围程序，包括输入、工具权限、历史管理、超时、停止、记录和验证。现代 coding agent 还有沙箱、会话、审批和上下文压缩。先读本项目的十几行控制流程，再顺着 [Codex 源码地图](codex-source-map.md) 读一次完整请求。工具接入数量不能单独说明可靠性。
